## 1. 文档概述

### 1.1 产品背景

内容生成/成片之后要落地：客户要么自己复制下载去发，要么走绑定账号自动发。但**自动发只对有开放 API 的平台成立**——抖音/企业号可真自动发，小红书/视频号无接口只能"导出+提醒手动发"。作品库是所有产出的归集与发布出口，必须**诚实地表达平台能力差异**，绝不吹"全平台一键自动发"（合规红线）。

本模块要解决的核心问题：**把脚本/图文/成片统一归集、可按平台/形态/合规/发布状态筛选，并提供"导出"与"发布"双模式**——发布按目标账号的自动发开关决定走真自动发还是退化为导出+提醒手动发。

> V1 不做：发布排期/定时、数据回流/效果归因、批量群发、跨平台一键分发。

### 1.2 产品目标

- 统一归集脚本/图文/成片，**多维筛选**（平台/形态/合规/发布状态）
- **导出**：下载/复制，全平台通用
- **发布**：走绑定账号；抖音真自动发，小红书/视频号退化导出+提醒手动发
- **合规状态**透传：有未处理提醒的作品醒目提示
- 诚实表达平台限制（不吹一键全平台）

### 1.3 核心指标

| 指标 | 目标值 |
|--|--|
| 导出成功率 | ≥ 99% |
| 抖音自动发成功率（已授权） | ≥ 95% |
| 无未处理合规提醒即发布占比 | 可统计/可拦 |
| 发布状态与平台实际一致 | 100% |

### 1.4 范围

**In-Scope（本期）**
- 作品列表 + 多维筛选
- 导出（下载/复制）
- 发布双模式（自动发 / 导出+提醒手动发）按账号开关
- 合规状态展示（有未处理提醒提示）
- 发布状态机
- **效果数据回流 + 赢家判定（2026-06-30 移入本期）**：有 API 平台自动回收、无 API 手动回填，据此判定「★赢家内容」（见 §4.5）——赢家依赖效果数据,不做回流就判不了赢家,故 V1 必做。

**Out-of-Scope（不做 / 后续）**
- 定时发布/排期、批量分发
- 小红书/视频号 RPA 半自动（留 V2，选型见 §11 social-auto-upload）

## 2. 用户与场景

### 2.1 目标用户
- **运营**：日常发布主力。
- **老板**：抽查、把关合规。

### 2.2 典型场景
1. 运营生成抖音脚本（已授权、自动发开）→ 作品库点「发布」→ 真自动发到抖音。
2. 小红书图文 → 点「发布」→ 因无接口，退化"导出文件 + 提醒手动发"。
3. 作品带"1 条未处理合规提醒" → 发布前提示先处理 → 处理后再发。
4. 老板按"待发布/已发布"筛选盘点本周产出。

### 2.3 用户故事
- 作为运营，我能一眼看到哪些作品已发、哪些待发、哪些有合规提醒。
- 作为运营，抖音能自动发我就不用手动，小红书系统老实告诉我得手动发。
- 作为老板，有合规提醒没处理的内容不该被随手发出去。

## 3. 整体方案

### 3.1 方案原则
- **双模式诚实**：能力到哪说到哪，自动发只对有 API 的平台。
- **合规前置**：有未处理提醒的发布给拦/提示（与合规预审一致，提醒式）。
- **归集统一**：脚本/图文/成片一个库、一套筛选。

### 3.2 模块结构
```
作品库
├─ 筛选条（平台 / 形态 / 合规状态 / 发布状态）
├─ 作品列表（标题·平台·形态·合规·发布状态·操作）
└─ 操作：编辑 / 导出 / 发布（按账号开关决定模式）
```

### 3.3 设计约束（功能限制）
1. **发布模式由目标账号自动发开关决定**（见 [[PRD_平台账号绑定]]）：开关开（仅抖音/企业号可开）→ 自动发；否则→导出+提醒手动发。
2. **小红书/视频号无 API**：永远只能导出+提醒，开关禁用。
3. **合规提醒未处理**：发布前提示（V1 提醒非阻断，可坚持发但有记录）。
4. **形态四类**：脚本/图文/成片/**公式**（公式=拆解产物，可筛选、可「用它新建」复用，不可发布）。
5. **禁止话术**："全平台一键自动发"等夸大表述。

## 4. 功能需求

### 4.1 列表 + 筛选
字段：标题 · 来源草稿 · 平台 · 形态 · 合规状态 · 发布状态 · 创建人/时间 · 操作
筛选：平台(抖音/小红书/视频号/快手) · 形态(脚本/图文/成片/公式) · 合规(无/有未处理/已处理) · 发布状态。

### 4.2 导出
- 下载（成片=视频、图文/脚本=文本/zip）或复制文案。
- 全平台通用；导出后状态→已导出。

### 4.3 发布（双模式）
| 目标账号 | 自动发开关 | 发布行为 |
|--|--|--|
| 抖音/企业号(已授权) | 开 | 真自动发 → 已发布 |
| 抖音/企业号(已授权) | 关 | 导出+提醒手动发 |
| 小红书/视频号 | 禁用 | 导出+提醒手动发 → 待手动发 |
| 未绑定/未授权 | — | 拦截，引导去绑定/授权 |
- 发布前：若作品"有未处理合规提醒"→ 提示先处理（可坚持发，记录）。

### 4.4 合规状态透传
- 来自内容创作的合规提醒状态（无/有未处理/已处理）在列表醒目展示，可筛。

### 4.5 效果数据回流 + 赢家判定（2026-06-30 新增·V1 必做）

**4.5.1 效果数据回收**
| 平台 | 回收方式 | 指标 |
|--|--|--|
| 抖音/企业号(有 API) | 定时/异步**自动拉取** | 播放 · 点赞 · 评论 · 收藏 · 完播率 · **线索(转化/私信/表单)** |
| 小红书/视频号(无 API) | **手动回填**(客户填 或 导出后跟踪) | 同上,能填多少填多少 |
- 回收数据写入 `work.metrics`(见 §6.1),带 `metrics_updated_at`;可多次刷新。

**4.5.2 赢家判定规则**
- **对象**：`publish_status=已发布` 且有效果数据的作品。
- **主指标 = 线索数**（获客北极星,最关联钱）;辅 = 互动(播放/点赞/收藏/完播)。
- **判定 = 相对该账号自身基线**(不用绝对值,防大小账号量级差异):
  - 基线 = 该账号(company × platform × form)**近 K 条内容的中位数**(线索 + 综合互动)。
  - **赢家条件**：线索数 或 综合互动 ≥ 基线 × N 倍(初值 N=2),或进该账号 top X%(初值 20%)。N/X **可配置,待数据校准**。
- 满足 → `is_winner=true`,记 `winner_score`(相对基线倍数/分位);有 API 自动判定,无 API 手动回填后同规则判定。

**4.5.3 赢家用途**
- 列表**★赢家标 + 排序加权**;作为**选题/复制依据**;**一键进「换人换产品」再生产**;其拆解公式回流复利(→作品库形态=公式)。

**4.5.4 边界**
- 数据不足(发布未满 X 小时/无回收) → 暂不判定,标"数据回收中"。
- 无 API 平台未回填 → 不自动判赢家,提示"回填数据以识别赢家"。

## 5. 状态流转（work.publish_status）
```
(草稿) ──导出──▶ (已导出)
       ──发布(自动)──▶ (发布中) ──▶ (已发布) / (发布失败·重试)
       ──发布(无API/开关关)──▶ (待手动发)
拦截：未绑定/未授权 → 不流转，引导授权
```
合法值：`草稿 / 已导出 / 已发布 / 待手动发 / 发布失败`

## 8. 技术考虑
- 自动发对接抖音官方内容发布 API（需资质，见 [[PRD_平台账号绑定]]）。
- 发布前查目标账号授权态 + 自动发开关（后台驱动的授权态为准）。
- 自动发为异步，状态回写；失败可重试。
- 合规提醒未处理的发布写记录（可追溯），便于复盘。

## 9. 风险与依赖

### 9.1 依赖
- 平台账号绑定（A9）：授权态与自动发开关。
- 抖音发布 API 资质（提前办）。
- 内容创作（作品来源 + 合规状态）。

### 9.2 风险
| 风险 | 应对 |
|--|--|
| 误以为全平台都能自动发 | 文案诚实 + 开关禁用 + 退化提醒 |
| 带未处理违禁内容发出 | 发布前提示 + 记录（V1 提醒） |
| 抖音发布 API 资质未办 | 提前办；未办前抖音也退化手动 |
| 发布状态与平台不一致 | 异步回写 + 失败重试 + 状态以回写为准 |

## 10. 验收标准
1. 作品可按平台/形态/合规/发布状态筛选，状态展示准确。
2. 导出对所有平台可用，导出后状态正确。
3. 已授权且开关开的抖音作品可真自动发；关或无 API 的退化为导出+提醒手动发。
4. 未绑定/未授权时发布被拦并引导授权。
5. 有未处理合规提醒的作品发布前被提示。
6. 产品文案不含"全平台一键自动发"类表述。
7. **效果数据回流**:抖音等有 API 平台自动回收播放/点赞/线索并写入 work.metrics;无 API 平台可手动回填。
8. **赢家判定**:据 §4.5 规则(主指标线索、相对账号基线倍数/分位)自动标 ★赢家,N/X 阈值可配置;数据不足时标"回收中"不误判;赢家可一键进换人换产品再生产。

## 11. V2 预研：小红书/视频号 RPA 半自动发布选型

> **状态**：预研选型，**非 V1 范围**（V1 这两个平台仍为"导出+提醒手动发"）。落地前必须先过可行性验证 + 合规告知双关卡。

### 11.1 背景与缺口

小红书/视频号**无对普通第三方开放的官方发布 API**（见 [[PRD_平台账号绑定]]），V1 只能"导出+提醒手动发"。V2 要把这两个平台从"纯手动"提升到"半自动辅助发布"，唯一可行路径是 **RPA（浏览器/UI 自动化模拟人操作）**。

### 11.2 选型：social-auto-upload（开源）

| 项 | 评估 |
|--|--|
| 项目 | `dreammis/social-auto-upload`（GitHub，开源） |
| 技术 | Python + Playwright/patchright，**Cookie 登录态** + 浏览器 RPA |
| 覆盖 | 抖音/小红书/视频号/快手/B站/TikTok/YouTube |
| 关键能力 | 多账号（一账号一 cookie 文件）、定时、CLI / Python 模块可被后端调用 |
| 接入方式 | 内容引擎产出成片/图文落盘 → 调其 CLI(`sau`) 或 uploader 模块发布 → 回写发布状态 |
| 价值 | **省自研发布层**；正好补我方"小红书/视频号无 API"的缺口 |

### 11.3 定位红线（与母版 [[AI 获客产品方案 Index]] RPA 边界一致）

1. **只当"发布补丁"，不当"截流引擎"**：仅用于**客户自己账号发自己内容**；严禁评论区批量引流、抓取他人数据（刑法 285 + 反不正当竞争双红线）。
2. **RPA 不解决合规，自带封号成本**：用的是**客户账号**，被风控判定 → 封客户号 → 砸招牌 + 可能赔偿。最大成本即在此。
3. **主平台仍走官方 API**：抖音坚持官方内容发布 API（企业认证），RPA 仅限小红书/视频号这类"官方无接口"的缺口。
4. **产品文案纪律**：对外定位"半自动辅助"，**禁止**吹"全自动规模化截流/一键发全平台"。

### 11.4 落地必备护栏（V2 工程要求）

- **拟人化**：随机节奏、控量，不暴力批量。
- **账号隔离**：单账号独立浏览器环境/指纹/IP（它支持一账号一 cookie，但环境隔离需自建）。
- **合规预审前置**：发布前过 LLM 违禁词过滤（与 [[PRD_后台_合规词库]] 同源）。
- **书面风险告知**：开通 RPA 发布前，向客户书面告知封号风险并留痕。
- **版本锁定**：fork 锁版本，仅取小红书/视频号两个 uploader，不直接吃上游 main（项目仍在重构、Web 端不保证可跑）。
- **失败兜底**：RPA 发布失败自动退化为"导出+提醒手动发"（复用 §4.3 / §5 状态机）。

### 11.5 风险

| 风险 | 应对 |
|--|--|
| 封客户号（最致命） | 拟人化 + 控量 + 账号隔离 + 书面告知 + 仅自有内容 |
| 平台 UI 改版致 RPA 崩 | 锁版本 + 专人跟版 + 失败退化手动 |
| 被当"截流工具"误用 | 产品层只开放"发自有内容"，不提供批量引流入口 |
| 合规越界 | 严守"自己账号 + 自有内容"边界，越界无任何豁免 |

### 11.6 V2 准入条件（先验证再开发）

1. 实测抖音/小红书/视频号三平台发布跑通 + 踩坑报告。
2. 单账号隔离环境方案验证（指纹/IP/cookie 不串）。
3. 合规与法务（律己）确认"自有账号发自有内容"边界 + 客户告知模板。
4. 三项通过方进入 V2 开发；否则维持 V1"导出+提醒手动发"。
