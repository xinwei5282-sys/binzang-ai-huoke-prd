## 1. 文档概述

### 1.1 产品背景

要"走绑定账号自动发"，前提是客户把自己的平台账号绑给系统并完成授权。但平台能力天差地别：**抖音/企业号有开放发布 API（需企业认证+申请权限+审核）能真自动发；小红书/视频号无开放接口，绑了也只能记录、只能手动发**。所以绑定页要做的不是"全都能自动发"的假象，而是**按平台诚实地控制自动发开关**——有 API 才可开，没 API 直接禁用。

本模块要解决的核心问题：**让客户绑定各平台账号、管理抖音的官方授权状态、并按账号控制"是否自动发布"开关**，为作品库的发布双模式提供授权态与开关依据。授权态由后台审核驱动（见 [[产品设计-殡葬V1-平台后台]] §八），商家端只读+操作申请。

> V1 不做：多账号矩阵管理、第三方代发服务、小红书/视频号 RPA、授权到期自动续。

### 1.2 产品目标

- 绑定抖音/小红书/视频号/快手账号
- 抖音走**官方 API 授权**（申请→后台审核→已授权）
- **自动发开关按账号控制**：仅有 API 平台（抖音/企业号）可开，其余禁用
- 标注用途（自有 2C / 小B 代做）
- 授权态/开关供作品库发布判定

### 1.3 核心指标

| 指标 | 目标值 |
|--|--|
| 抖音授权完成率（资质齐全） | ≥ 90% |
| 自动发开关与平台能力一致 | 100%（无 API 禁用） |
| 授权失效可感知/可重授 | 100% |

### 1.4 范围

**In-Scope（本期）**
- 账号绑定（新增/查看/解绑）
- 抖音官方授权申请 + 状态展示（后台审核驱动）
- 自动发开关（按账号，能力受控）
- 用途标注

**Out-of-Scope（不做 / 后续）**
- 小红书/视频号自动发 / RPA
- 多账号矩阵、代发服务
- 授权自动续期

## 2. 用户与场景

### 2.1 目标用户
- **老板（管理员）**：绑定权归管理员（运营不可碰，见 [[PRD_账号与成员]]）。

### 2.2 典型场景
1. 老板绑抖音 → 提交企业认证资料申请授权 → 后台审核通过 → "已授权" → 自动发开关可开。
2. 老板绑小红书 → 系统标"无 API·仅手动"，自动发开关禁用。
3. 抖音授权失效 → 显示"已失效" → 老板重新申请。
4. 老板把某抖音号标"自有 2C"，另一个标"小B 代做"。

### 2.3 用户故事
- 作为老板，我绑了抖音并通过授权后就能让系统自动发，省事。
- 作为老板，小红书绑了系统老实告诉我只能手动，我不抱错期望。
- 作为老板，授权失效我能看到并重新授权。

## 3. 整体方案

### 3.1 方案原则
- **能力诚实**：自动发开关由平台 API 能力决定，没 API 直接禁用。
- **授权后台驱动**：抖音授权态以后台审核结果为准，商家端只读。
- **开关即依据**：作品库发布读此开关决定自动/手动。

### 3.2 模块结构
```
平台账号绑定
├─ 已绑账号卡片（平台·账号·授权状态·用途·自动发开关）
├─ 绑定新账号（选平台 + 账号信息 → 授权/记录）
└─ 抖音授权（申请 → 后台审核 → 已授权/失效/驳回）
```

### 3.3 设计约束（功能限制）
1. **发布能力受控**：按账号实时 capability 展示官方 API、RPA、手动；无能力的方式禁用，不能只按平台名称判断。
2. **抖音需官方授权**：企业认证+权限审核（后台驱动），未授权不可开自动发。
3. **绑定权限**：仅管理员。
4. **授权态只读**：商家端展示后台审核结果，不能自己点成"已授权"。
5. **用途标注**：自有 2C / 小B 代做（影响合规边界，代运营 C 端需 PIPL DPA）。

## 4. 功能需求

### 4.1 已绑账号卡片
字段：平台 · 账号名/ID · 授权状态(已授权/待授权/已失效/驳回/仅记录) · 用途 · 自动发开关。
| 平台 | 授权 | 自动发开关 |
|--|--|--|
| 抖音/企业号 | 需官方授权 | 已授权才可开 |
| 小红书/视频号 | 记录账号、授权和能力 | 按账号 capability 展示 RPA/手动等已验证方式 |

### 4.2 绑定新账号
选平台 + 填账号名/ID → 抖音引导走授权申请；其余直接记录（标仅手动）。

### 4.3 抖音授权
- 申请：提交企业认证资料 → 状态"待审核/审核中" → 后台审 → 已授权/驳回。
- 已授权：显示有效期；失效→可重新申请。
- 授权态全部由后台审核回填，商家端只读（见 [[产品设计-殡葬V1-平台后台]]「抖音授权审核」）。

### 4.4 自动发开关
- 抖音已授权 → 可开/关；开后作品库发布走自动发。
- 无 API 平台 → 开关禁用，点击提示"该平台无开放接口，仅手动"。

## 5. 状态流转（binding.auth_status）
```
抖音：(待授权) ──申请──▶ (审核中) ──后台通过──▶ (已授权) ──失效──▶ (已失效) ──重申──▶ 审核中
                                  └──后台驳回──▶ (驳回) ──补件重申──▶ 审核中
小红书/视频号：(仅记录) —— 无授权流程，自动发恒禁用
```
自动发开关 enabled 仅在 `已授权` 且平台有 API 时可置 true。

## 8. 技术考虑
- 抖音对接官方内容发布 API：企业认证 + 权限申请 + 审核（有周期，提前办，见 [[产品规划-殡葬V1]] §六）。
- 授权态以后台审核为单一真相，商家端轮询展示，禁止前端自置已授权。
- 自动发开关后端二次校验（has_api && 已授权），防绕过。
- 用途=小B代做时，提示签 PIPL DPA（合规，见 [[产品设计-殡葬V1-页面与字段]] §七）。

## 9. 风险与依赖

### 9.1 依赖
- 后台抖音授权审核（驱动授权态）。
- 抖音官方 API 资质。
- 作品库（消费授权态/开关）。

### 9.2 风险
| 风险 | 应对 |
|--|--|
| 客户误期望小红书自动发 | 开关禁用 + 明确"仅手动"文案 |
| 抖音资质未办自动发不可用 | 提前办；未办前抖音也仅手动 |
| 授权失效后仍自动发失败 | 失效即关开关 + 提示重授 |
| 代运营 C 端合规风险 | 用途标注 + DPA 提示 |

## 10. 验收标准
1. 可绑定多个平台且同平台多个账号；每个账号准确显示已经验证的发布能力。
2. 抖音可提交授权申请，授权态由后台审核驱动、商家端只读展示（待审/已授权/驳回/失效）。
3. 任一发布方式都必须满足账号已授权且 capability 支持，并由后端二次校验防绕过。
4. 授权失效可感知并可重新申请。
5. 绑定操作仅管理员可见可用。
6. 自动发开关状态正确供作品库发布判定。

## 11. 多平台多账号专项需求（v3.1 · 2026-08-13）

### 11.1 多平台多账号

支持公众号、抖音、小红书；同一租户在同一平台可绑定多个账号。账号成为独立业务对象，任务、内容、发布记录和指标必须引用 `publishing_account_id`。

### 11.2 发布能力

- 公众号：官方 API、RPA、手动；具体能力由授权范围返回。
- 抖音、小红书：RPA、手动；不得伪装为官方 API。
- 账号状态：`pending | authorized | expired | disabled`。
- 创建发布任务时按“平台 → 账号 → 账号支持的发布方式”三级联动。

### 11.3 安全与授权

系统不保存或展示 RPA 目标平台明文密码；只保存受控会话引用、授权范围和到期时间。解绑前提示受影响的草稿与任务；历史发布记录保留账号快照。

### 11.4 接口与验收

- `GET/POST /publishing/accounts`：查询/绑定账号。
- `GET /publishing/accounts/{id}/capabilities`：返回发布与指标能力。
- `POST /publishing/accounts/{id}/reauthorize`：重新授权。
- 验收：同平台两个账号可同时存在；创建任务只能看到本租户账号；账号/方式不匹配时后端拒绝；到期账号不能新建发布任务。

### 11.5 开发执行契约

- `publishing_account` 必须包含 tenant_id、platform、display_name、external_account_ref、auth_status、capabilities、credential_ref、expires_at、last_checked_at。
- 明文 token、Cookie、密码不得返回前端或进入 Prompt/日志；凭证服务只返回引用和授权范围。
- 解绑、过期、能力变化必须重新校验未执行任务；历史发布记录保留账号快照。
- 埋点：绑定开始/成功/失败、重授权、解绑、能力刷新、任务因账号能力被阻断。
