# 会议纪要与企业知识边界调整设计

## 1. 目标

将现有“企业记忆”收窄并更名为“会议纪要”，只处理用户上传的会议音频或视频，产出可回听、可校对、可追溯的会议文本与结构化总结。聊天截图、PDF、Word、TXT、粘贴文本等非会议资料统一进入“企业知识”的资料处理流程。

本轮继续修改可点击原型，不接入真实对象存储、ASR、LLM 或消息发送服务；页面必须明确显示“原型演示”或“模拟生成”。

## 2. 产品边界

### 会议纪要

- 入口位置：企业大脑 / 会议纪要。
- 接收格式：音频和视频，不接收图片、PDF、Word、TXT或普通粘贴文本。
- 核心产物：音视频来源、处理进度、带说话人和时间戳的转写文本、会议总结、关键决策、行动项、客户意向及证据。
- 人工控制：用户可校对说话人和文本；行动项经确认后才进入“工作中枢 / 我的待办”。
- 知识关系：会议内容默认只保存在会议纪要；从会议中提取的企业事实、规则或项目要求，经过人工确认后才能进入企业知识。

### 企业知识

- 接收格式：聊天截图、图片、PDF、Word、TXT、网页资料和粘贴文本。
- 核心产物：来源记录、解析结果、候选事实、冲突项及已确认知识。
- 不承担会议音视频转写和会议纪要展示。
- 未确认的 OCR、文档解析或 AI 推断不得成为正式企业事实。

## 3. 信息架构调整

- 企业大脑二级入口“企业记忆”更名为“会议纪要”。
- 页面标题调整为“会议纪要”，说明为“音视频 · 转写 · 总结 · 行动项”。
- 原 `kb-memory` 页面键保留，避免破坏既有路由和页面 PRD 抽屉映射；用户可见名称全部更新。
- “企业知识”页面强化“上传聊天记录或文件”入口，并明确支持图片、文档和粘贴文本。
- 工作中枢继续承担所有已确认行动项和生成任务，会议纪要不另建任务列表。

## 4. 会议处理流程

```text
选择音频/视频
  → 校验格式与大小
  → uploaded
  → extracting_audio
  → transcribing
  → diarizing
  → summarizing
  → ready | failed
  → 用户查看/校对
  → 确认行动项
  → 工作中枢待办
```

原型中可以压缩显示为“上传完成、文本提炼中、总结生成中、已完成、处理失败”，但内部演示对象保留上述阶段语义。

重复确认同一行动项必须幂等；任务保留 `sourceMeetingId`、时间戳证据和客户/项目关联。

## 5. 会议纪要页面设计

### 列表页

每条会议显示：

- 文件名、音频/视频类型和会议时长；
- 上传账号、可见范围、客户和项目关联；
- 当前处理阶段和失败原因；
- 摘要预览、行动项数量；
- “查看会议纪要”或“重试处理”。

主按钮为“上传会议音视频”，文件选择器只接受 `audio/*,video/*`。

### 详情页

详情按以下顺序组织：

1. 来源与关联；
2. 音视频播放器及处理状态；
3. 带时间戳和说话人标签的转写文本；
4. 会议总结；
5. 关键决策；
6. 行动项；
7. 客户意向和对应证据；
8. “确认行动项并加入待办”。

摘要和行动项均标记为 AI 提取结果，允许用户修改后确认。

## 6. 企业知识上传调整

企业知识上传入口显示四类来源：

- 聊天记录：聊天截图或导出的聊天文本；
- 文件资料：PDF、Word、TXT；
- 图片资料：业务截图、证照或宣传材料；
- 文本资料：直接粘贴内容或网页文本。

如果用户误将音频/视频拖入企业知识，应提示“会议音视频请前往会议纪要处理”，并提供跳转按钮。会议纪要页面误传文档时，同样提示前往企业知识。

## 7. 账号与权限

- 会议纪要继续按账号、项目和企业范围区分 `private | project | enterprise`。
- 员工上传的私有会议默认仅本人可见；关联共享项目后，项目成员可见。
- 企业知识沿用知识域和企业权限；个人未共享资料不得进入企业知识检索。
- 老板可查看企业级会议，不代表能够自动读取员工私人会议。

## 8. 开源技术参考与选型

### 推荐组合

- 中文主转写：[FunASR](https://github.com/modelscope/FunASR)，使用中文 ASR、VAD、标点和说话人能力；工具代码为 MIT，具体模型上线前单独核对许可证。
- 多语言备用：[faster-whisper](https://github.com/SYSTRAN/faster-whisper)，MIT。
- 时间戳处理参考：[WhisperX](https://github.com/m-bain/whisperX)，BSD-2-Clause。
- 高级说话人分离参考：[pyannote.audio](https://github.com/pyannote/pyannote-audio)，代码 MIT；预训练模型需要接受 Hugging Face 条款。
- 产品交互参考：[MeetMemo](https://github.com/NotYuSheng/MeetMemo)，MIT，参考上传、转写进度、同步播放、说话人编辑和摘要流程。

不直接嵌入 [zabt.ai](https://github.com/afeef/zabt-ai)，因为其 AGPL-3.0 许可证会给闭源商业 SaaS 带来额外开源义务。Scriberr 可作为交互参考，但其维护者已公开说明当前暂停开发，不作为核心依赖。

## 9. 异常处理

- 格式不支持：保留用户选择结果，明确提示正确入口。
- 文件过大或时长过长：提示限制和建议压缩，不进入伪处理状态。
- 转写失败：显示失败阶段、原因和重试按钮，已完成阶段不重复执行。
- 说话人识别不准确：允许合并、重命名或标记“未知说话人”。
- 总结失败：保留完整转写，只重试总结，不重新上传或转写。
- 行动项重复确认：复用已有任务并提示，不重复创建。

## 10. 验收标准

- 用户可见的“企业记忆”全部改为“会议纪要”。
- 会议纪要上传控件只接受音频和视频。
- 页面可演示“上传 → 文本提炼 → 总结 → 查看纪要 → 确认行动项 → 待办”的完整闭环。
- 会议详情同时包含转写文本、说话人、时间戳、总结、决策和行动项。
- 企业知识明确接收聊天记录、图片、PDF、Word、TXT和粘贴文本。
- 音视频与普通资料误传时均提供正确入口提示。
- 老板和员工账号的数据范围保持区分。
- 原型、页面 PRD、标题契约和浏览器验收脚本使用一致术语。
- 1440×900 与 390×844 均无页面横向溢出、控制台异常或主操作裁切。

## 11. 非本轮范围

- 真实 ASR、说话人模型和 LLM 接口接入；
- 会议机器人自动入会或实时录音；
- 真实文件存储、计费、配额和转写时长限制；
- 自动把会议结论写成企业知识；
- 自动发送会议纪要或行动项通知。
